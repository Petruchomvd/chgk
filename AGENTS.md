# CHGK Project — Инструкции для Codex

## Сохранение планов реализации

Когда ты входишь в plan mode и составляешь план реализации задачи:

1. **Сохрани план** как файл в `docs/plans/` с именем `YYYY-MM-DD-<краткое-описание>.md`
   - Пример: `docs/plans/2026-02-28-parallel-classification.md`
2. **Формат файла:**
   ```markdown
   # <Название задачи>

   **Дата:** YYYY-MM-DD
   **Статус:** В работе | Выполнен | Отложен

   ## Контекст
   <Зачем это нужно>

   ## План
   <Шаги реализации — то, что было в plan mode>

   ## Затронутые файлы
   <Список файлов, которые будут изменены>

   ## Результат
   <Заполняется после реализации>
   ```
3. **Сохраняй план ДО начала реализации** (сразу после выхода из plan mode)
4. **Обнови статус и раздел "Результат"** после завершения работы

Папка `docs/plans/` — архив всех планов реализации. Это помогает отслеживать историю решений и причины изменений в проекте.

## Ведение Changelog

При каждом значимом изменении проекта обновляй `docs/changelog/CHANGELOG.md`:

1. **Когда обновлять:** после коммита с новой функциональностью, исправлением багов или изменением архитектуры
2. **Формат записи:**
   ```markdown
   ## [YYYY-MM-DD] — Краткое описание

   ### Добавлено
   - Новые функции и файлы

   ### Изменено
   - Модификации существующего кода

   ### Исправлено
   - Баг-фиксы

   ### Удалено
   - Удалённый функционал
   ```
3. **Новые записи добавляются в начало** файла (после заголовка), старые остаются ниже
4. Указывай хэши коммитов в разделе «Коммиты» для трассируемости

## Хранение рабочих баз

- Никогда не добавляй `*.db`, `*.db-wal` или `*.db-shm` в Git, GitHub или Git LFS.
- После развёртывания основной экземпляр `chgk_analysis.db` и рабочий `training.db` находятся на сервере вне Git-клона.
- На компьютере Матвея хранится проверенная резервная копия с сервера; локальная БД в папке проекта допустима только до переноса или для проверки резервной копии.
- Серверные пути задаются через `CHGK_DB_PATH` и `CHGK_TRAINING_DB_PATH`.
- GitHub является только необязательным зеркалом исходного кода. Запуск, развёртывание и восстановление проекта не должны зависеть от наличия базы в GitHub.
- Активную SQLite-базу нельзя копировать вслепую. Сначала создай согласованный снимок средствами SQLite, затем передавай и проверяй копию.
