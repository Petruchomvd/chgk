## [2026-07-18] — Качественные «берущиеся» факты по темам

Факты в досье «Учить» были кривыми: показывались комментарии к вопросам —
фрагменты, привязанные к своему вопросу, не читаемые как самостоятельные факты.
Исследование (docs/plans/2026-07-18-quality-facts.md) показало: источники
комплементарны — Wikipedia-лид даёт чистое ЯДРО, а корпус (вопросы+разборы) —
ходовые ЗАЦЕПКИ, которые эксплуатирует ЧГК.

### Добавлено

- `scripts/gen_facts.py` — генератор карточек: для канон-ответа собирает
  (A) Wikipedia + (B) корпусные углы, LLM (gemma@openrouter) синтезирует
  `{ядро, зацепки[{факт, угол, цитата}]}`. Антигаллюцинация без второй модели:
  модель обязана дать дословную цитату-опору, Python проверяет перекрытие её слов
  с сырьём (порог 0.6) — факт без опоры в учебник не идёт. Кэш
  `data/facts/fact_cards.json`, инкрементально, с паузами. Флаги `--weak`
  (канон слабых тем), `--category-ids`, `--answers`, `--per-cat`.
- `/api/study/fact` теперь отдаёт `card` (ядро + подтверждённые зацепки), если
  сгенерирована; страница «Учить» показывает карточку сверху, вопросы — ниже
  как примеры.

### Стоимость

~$0.0003 на сущность (gemma). Канон слабых тем (~64 сущности) — ~$0.02.

## [2026-07-18] — Контур «Учить»: корпус вопросов как учебник

Инструмент умел проверять память (тренировка), но не давал набирать эрудицию —
а именно эрудиция оказалась слабостью команды. Добавлен контур обучения: корпус
превращён в учебник без нового LLM (объяснение факта уже лежит в комментариях —
их имеют 89% вопросов, 188k из 212k).

Идея: в ЧГК десятки ответов повторяются из турнира в турнир (Герострат, гильотина,
Ной, зеркало, Пушкин…), и каждый спрашивают с разных сторон. «Досье факта» = все
вопросы с этим ответом = все углы + готовые разборы. Учить приоритетно то, где
команда отстаёт от поля.

### Добавлено

- `app/study.py` — `canon(category_id)`: повторяющиеся ответы темы (что нужно
  знать) с частотой; `fact_dossier(answer)`: все углы вопроса + разбор из
  комментов, отсортированы по сложности (трудные — учебнее). Кириллический
  регистр через регистрируемый `pylower` (SQLite LOWER/LIKE кириллицу не сворачивает).
- Эндпоинты `/api/study/canon`, `/api/study/fact`.
- Веб-страница «Учить» (`/study`): выбор темы (слабые темы команды помечены ●
  и идут первыми), канон ответов, досье факта с углами и разбором, отметка
  «изучил» (localStorage). Пункт навигации.
- Петля учить→тренировать: кнопка «тренировать факт» на досье запускает сессию
  активного припоминания по вопросам с этим ответом (`start_by_answer`,
  режим `study_fact`, поле `answer` в StartRequest). Пассивное чтение → активный
  recall, что и учит.

## [2026-07-18] — Досье команды: модель игры из полной истории rating.chgk

Узкое место проекта было в тонком сигнале о собственной игре: внутренних попыток
почти нет (72 записи, 1 игрок), а диагноз слабостей держался на 132 вопросах из
3 турниров (n=2..12 на категорию — шум). Гипотеза подтвердилась: rating.chgk
отдаёт маски всех команд по каждому турниру, поэтому дефицит «команда vs поле»
считается прямо по маскам, без привязки к нашей БД. Текущий состав сыграл 8
турниров (6 с масками) → 394 сыгранных вопроса вместо 132.

Разбор гипотез и находок: `docs/plans/2026-07-18-team-model-from-rating.md`,
отчёт — `docs/reports/team-97700-history.md`.

### Добавлено

- `scripts/team_history.py` — авто-досье команды: тянет все турниры из
  `api.rating.chgk.info`, считает дефицит по каждому, **калибровочную кривую**
  (где на шкале сложности теряются очки) и `focus_band`. Матчит турниры к пакетам
  БД по корреляции беручести (порог 0.85, язык-независимо — по числу вопросов и
  дате), с фолбэком на маску gotquestions для пакетов, потерявших маску в рейтинге.
- Калибровочная модель `P(команда берёт | беручесть поля)` — логистическая
  регрессия в логит-шкале (a=−0.196, b=1.07, n=394). Режимы `--forecast <pack>`
  (прогноз счёта + swing-вопросы) и `--validate` (leave-one-tournament-out:
  средняя ошибка ~7 вопросов, вся — из одного турнира-выброса).
- Веб-страница «Досье команды» (`/team`): калибровочная кривая, история турниров,
  прогноз счёта на любой пакет со swing-вопросами, слабые темы (n≥5).
  Эндпоинты `/api/team/dossier`, `/api/team/forecast`.

### Изменено

- `app/training_engine.py` — `start_team_gap` берёт зону сложности из
  `focus_band` профиля (посчитана по калибровке команды: 30–60% беручести,
  а не угаданные 35–70%) и отбирает слабые темы только с надёжной выборкой (n≥5),
  отсекая шумовые категории n=1..2.
- `data/team/team-97700-gaps.json` перегенерирован из 6 турниров (было 3):
  добавлены блоки `calibration`, `calibration_model`, `focus_band`, дефицит по
  каждому турниру. Старый профиль сохранён рядом (`-3tourn-backup`, `-old`).

### Находки (проверенные гипотезы)

- Дефицит команды сконцентрирован в полосе 20–60% беручести (−6.6 и −6.8 п.п.):
  на лёгких вопросах команда обыгрывает поле (+2.0), на трудных идёт вровень.
  Вывод: слабость не в дисциплине и не в потолке знаний, а в «средних» вопросах.
- Замены — сильная сторона (−0.077/в против −0.180/в на чистом знании);
  главная дыра — эрудиция (Быт, Кино, Наука, Музыка, История).
- Позиционный эффект в туре — статистический шум (не используется).

## [2026-07-16] — Веб-приложение «Картотека»: редизайн и сохранение прогресса

Полный редизайн учебного контура. Веб-тренировка раньше писала результаты только
в `st.session_state` и теряла их при закрытии вкладки; движок обучения с Leitner
(`app/training_engine.py`) использовал только Telegram-бот. Теперь веб работает
на том же движке, и история у бота и веба общая.

Подробности и разбор находок: `docs/plans/2026-07-16-web-redesign-kartoteka.md`.

### Добавлено

- `api/` — FastAPI-слой поверх существующих модулей (`main.py`, `catalog.py`).
  Тонкая обёртка: логика обучения переиспользуется, а не дублируется.
- `web/` — React 19 + Vite + TypeScript + Tailwind v4 + shadcn/ui.
  Разделы: Обзор, Картотека, Темы, Тренировка, Повторение, страница вопроса.
- Дизайн-система «Картотека»: графитово-синяя навигация, тёплый бумажный фон,
  приглушённый янтарный акцент, serif для длинных текстов вопросов.
  Все текстовые пары проверены по контрасту (5.3–14.4, WCAG AA).
- Управление с клавиатуры в тренировке: `Enter` — показать ответ, `1`/`2` — оценка,
  `/` — фокус в поиск.
- Фильтр по статусу изучения (не встречался / был / ошибался / знал / к повторению)
  — через `ATTACH` `training.db` к базе вопросов.
- `scripts/run_web.sh` — запуск API и фронтенда одной командой.
- `requirements-web.txt`.

### Изменено

- Сортировка каталога по умолчанию — свежие турниры (`published_date DESC`)
  вместо `id DESC`: последний выносил наверх импорт без дат (938 вопросов).
- Streamlit-дашборд остаётся инструментом аналитики классификации и не тронут.

### Исправлено

- Веб-тренировка не сохраняла ни попытки, ни Leitner — теперь пишет в `training.db`
  под тем же `user_id`, что и бот.
- Дубли в списке вопросов: в новом API одна строка на вопрос
  (`ROW_NUMBER() OVER (PARTITION BY question_id)`).
  В `dashboard/db_queries.search_questions` баг остался — нужен отдельный фикс.
- При недоступном API интерфейс показывал «База ещё не классифицирована»
  вместо ошибки (React Query: `fetchStatus: 'paused'` при `error: null`).
- Согласование числительных: «1 вопрос ждёт повторения», «1 вопрос пройден».

  фильмов → `data/soviet_cinema/people.json`. После фильтров — 6 416 человек.

  («в какой роли упомянут») — разные измерения и не смешиваются.

  (режиссёр одного фильма) перехватывал 76 вопросов про Чарли Чаплина.
- **Разворот инвертированных имён:** «Гайдай, Леонид Иович» → «Леонид Иович

  403 отсеянных человека.
- В отчёте колонки по полям считали упоминания, а «Вопросов» — вопросы,
  из-за чего выходило «104 в киноконтексте при 76 вопросах». Теперь везде вопросы.

- 46 653 упоминания. Подтверждённых (high): 4 216 вопросов с людьми кино,
  2 824 с фильмами, 520 с персонажами.
