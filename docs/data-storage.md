# Хранение рабочих баз CHGK

## Принятая схема

`chgk_analysis.db` и `training.db` являются рабочими данными, а не исходным кодом.

- После развёртывания основная рабочая копия обеих баз находится на личном сервере.
- На Mac хранится проверенная резервная копия, полученная с сервера.
- Git, GitHub и Git LFS не используются для хранения или доставки баз.
- GitHub остаётся необязательным зеркалом исходного кода. Проект должен запускаться, обновляться и восстанавливаться без базы в GitHub.

До развёртывания текущая `chgk_analysis.db` в корне проекта остаётся исходной копией для переноса. После успешного переноса локальная копия считается резервной или тестовой, а не основной.

## Серверные пути

Рабочие базы следует хранить вне Git-клона:

```env
CHGK_DB_PATH=/var/lib/chgk/chgk_analysis.db
CHGK_TRAINING_DB_PATH=/var/lib/chgk/training.db
```

Каталог `/var/lib/chgk/` должен существовать и быть доступен на чтение и запись только пользователю, от которого запускаются приложения CHGK.

Относительные пути `chgk_analysis.db` и `training.db` предназначены только для локальной разработки или проверки скачанной резервной копии.

## Первоначальный перенос на сервер

1. Остановить запись в локальные базы или создать согласованные снимки средствами SQLite.
2. Передать снимки на сервер отдельным защищённым способом.
3. Поместить их в постоянный каталог вне папки с кодом.
4. Задать `CHGK_DB_PATH` и `CHGK_TRAINING_DB_PATH` в серверном окружении.
5. Выполнить `PRAGMA quick_check` для обеих копий.
6. Проверить сайт, бота, запись результата тренировки и повторное открытие прогресса.
7. Только после этих проверок считать сервер основной точкой хранения.

## Резервирование с сервера на Mac

1. На сервере создаётся согласованный SQLite-снимок каждой базы. Нельзя просто копировать активно изменяемый файл вместе с неизвестным состоянием WAL.
2. Снимки передаются на Mac в `/Users/User/Desktop/myos/90_Архив/резервные_копии/chgk/`.
3. Имена содержат дату и время, отдельно для `chgk_analysis` и `training`.
4. После передачи выполняется `PRAGMA quick_check`.
5. Хранятся несколько последних проверенных поколений с учётом свободного места; старые копии удаляются только после проверки более новой.
6. Периодически выполняется пробное восстановление, а не только проверка наличия файлов.

Внутренние каталоги `.backups/` и `data/backups/` полезны перед массовыми операциями, но не заменяют резервную копию на другом устройстве и не отправляются в Git.

## Git и старая история LFS

- `.gitignore` исключает `*.db`, `*.db-wal` и `*.db-shm`.
- В новых коммитах база не отслеживается через LFS.
- Старые LFS-объекты остаются только историческим наследием. Переписывать историю или восстанавливать доставку базы через GitHub сейчас не нужно.
- После появления проверенной схемы «сервер + Mac» локальный кэш `.git/lfs` можно удалить отдельной операцией, если понадобится освободить место.
