# План стабилизации и пайплайна сложности

**Дата:** 2026-07-15  
**Статус:** реализовано, полный backfill основной базы завершён 2026-07-16  
**Главная цель:** сделать безопасное обновление базы и расчёт сложности вопросов одной командой, сохранив происхождение показателя и понятные причины пропусков.

## 1. Зафиксированные ограничения

До отдельного аудита запрещено автоматически:

- удалять или объединять дубликаты;
- заполнять отсутствующие тексты, ответы, комментарии, источники и авторов;
- удалять неполные вопросы или пакеты;
- присваивать сложность вопросам без результатов команд;
- частично сопоставлять маску результатов с вопросами «по приблизительному порядку».

Разрешённая будущая операция — расчёт сложности только там, где есть проверяемые результаты и однозначное соответствие позиций маски вопросам.

## 2. Что выяснено о сложности

На момент первичного аудита в базе GotQuestions:

- 3,997 разобранных пакетов и 211,841 вопрос;
- 2,816 пакетов содержат `teams_played > 0`; в них 126,780 вопросов;
- 1,181 пакет не содержит сведений об игравших командах; в них 85,061 вопрос;
- 1,425 пакетов не имеют пакетной сложности trueDL;
- из них 244 пакета сообщают число команд, но не имеют trueDL;
- поле `questions.difficulty` пусто у всех вопросов.

Причина последнего пункта — не только новые или несыгранные пакеты. Расчёт вопросной сложности существует как отдельный `scripts/scrape_difficulty.py`, но не входит в основной процесс обновления и, судя по базе, не был выполнен для каталога.

Текущий скрипт нельзя просто запустить на производственной базе без исправлений:

- он хранит только итоговое число и не хранит число команд, число взятий, метод и дату расчёта;
- разрешает расхождение длины маски и количества вопросов до 20% и после этого записывает частичный результат;
- при неодинаковой длине масок считает отсутствующую позицию неправильным ответом;
- сопоставляет позиции по `ORDER BY tour_number, number`, а не по порядку ID вопросов в исходной странице;
- смешивает понятия пакетного trueDL и простой сложности по доле взятий;
- не хранит состояния `ждём результатов`, `результатов не будет`, `несовпадение`, `временная ошибка`;
- не вызывается основным парсером.

## 3. Семантика показателей

На первом этапе для вопроса рассчитывается наблюдаемая сложность по доле взятий:

```text
take_rate = correct_teams / total_teams
difficulty_raw = 10 × (1 - take_rate)
```

Где 0 означает, что вопрос взяли все команды, а 10 — что не взяла ни одна.

Этот показатель нельзя называть trueDL: он не учитывает силу команд. `packs.difficulty` остаётся пакетным trueDL, полученным с GotQuestions. Если позднее появятся рейтинги участвовавших команд, скорректированная вопросная сложность станет отдельным методом и не перезапишет исходную долю взятий.

## 4. Изменения модели данных

### 4.1. Порядок вопросов

Добавить `questions.position_in_pack`. Новый парсер заполняет его непосредственно по порядку вопросов в payload страницы пакета.

Для старых пакетов порядок восстанавливается не по номеру вопроса, а повторным чтением страницы пакета: ID вопросов из payload сопоставляются с ID в базе. Если множества ID различаются, пакет получает статус `content_mismatch`, а сложность не записывается.

### 4.2. Статистика вопроса

Создать таблицу `question_result_stats`:

- `question_id`, `pack_id`, `position_in_pack`;
- `correct_teams`, `total_teams`;
- `take_rate`, `difficulty_raw`;
- `method` (`take_rate_v1` или `embedded_question_stats_v1`);
- `source_url`, `source_hash`;
- `calculated_at`.

`questions.difficulty` можно оставить совместимым кэшем `difficulty_raw`, но каноническими данными должны быть числитель, знаменатель и метод. Это позволит проверить и пересчитать показатель.

### 4.3. Состояние обработки пакета

Создать таблицу `pack_result_status`:

- `pack_id`;
- `status`;
- `attempt_count`, `last_attempt_at`, `next_retry_at`;
- `teams_found`, `mask_count`, `mask_length`, `question_count`;
- `source_hash`, `last_error`.

Статусы:

- `pending` — ещё не проверяли;
- `complete` — рассчитаны все зачётные игровые позиции; явные разминки могут остаться без сложности;
- `partial_complete` — проверяемая статистика рассчитана не для всех вопросов пакета: остались дополнительные вопросы вне игровой маски или вопросы без полных встроенных счётчиков;
- `waiting_for_results` — пакет новый, результатов пока нет;
- `no_results` — старый пакет без результатов, регулярный повтор не нужен;
- `content_mismatch` — набор вопросов на сайте и в базе различается;
- `mask_mismatch` — длина/структура масок не совпадает с вопросами;
- `retryable_error` — сеть или временная ошибка;
- `not_applicable` — внешний импорт, для которого GotQuestions не является источником результатов.

## 5. Безопасный алгоритм сложности

Для каждого подходящего пакета:

1. Получить или переиспользовать HTML пакета и извлечь упорядоченный список ID вопросов.
2. Проверить, что список полностью совпадает с вопросами этого пакета в базе.
3. Получить `/table/{pack_id}` и извлечь маски структурным разбором Next.js payload, а не широкой регуляркой по HTML.
4. Проверить, что все маски имеют одинаковую допустимую длину.
5. Проверить точное соответствие длины маски числу зачётных позиций.
6. Рассчитать `correct_teams`, `total_teams`, `take_rate` и `difficulty_raw`.
7. Если позиционное сопоставление маски невозможно, разрешить только ID-связанный fallback из payload вопросов: одинаковая выборка турниров и команд у всех вопросов, положительное число команд, точное совпадение общего числа команд с количеством строк таблицы, допустимое число взятий и совпадение серверной сложности с долей взятий.
8. Одной транзакцией записать все подтверждённые статистики и удалить устаревшие производные значения для вопросов, не прошедших текущую проверку.
9. При любой ошибке соответствия не записывать неподтверждённые значения сложности; сохранить диагностический статус.
10. При изменении `source_hash` безопасно пересчитать статистику: результаты могут меняться после исправлений и апелляций.

Для нового пакета без результатов назначать повторную проверку с увеличивающимся интервалом. Старые исторические пакеты без команд после контрольной попытки переводить в `no_results`, чтобы каждый запуск не запрашивал их заново.

## 6. Единая команда

Целевая повседневная команда:

```bash
python scripts/update_catalog.py
```

Она выполняет этапы последовательно:

1. Проверка схемы и целостности базы.
2. Безопасная резервная копия перед миграцией или массовым backfill.
3. Поиск и парсинг только новых пакетов и разрешённых повторных попыток.
4. Расчёт сложности для новых пакетов с результатами.
5. Обработка очереди ранее пропущенной сложности.
6. Контроль, что количество вопросов и тематических меток не уменьшилось.
7. Итоговый отчёт: новые пакеты, новые вопросы, рассчитанная сложность, ожидающие результаты, несовпадения и ошибки.

Дополнительные режимы:

```bash
python scripts/update_catalog.py --dry-run
python scripts/update_catalog.py --difficulty-only
python scripts/update_catalog.py --backfill-difficulty
python scripts/update_catalog.py --pack 6900 --dry-run
```

Обычный запуск должен обрабатывать новые и уже наступившие повторные попытки. Полный первоначальный обход 2,816 пакетов запускается отдельно через `--backfill-difficulty`, но это всё равно одна управляемая команда, а не ручная цепочка скриптов.

## 7. Порядок исправлений

### Этап A — защита данных

1. Заменить разрушающий `INSERT OR REPLACE` пакетов на настоящий UPSERT через `ON CONFLICT(id) DO UPDATE`.
2. Объединить обновление пакета, вопросов и статуса в одну транзакцию.
3. Исправить подсчёт реально вставленных вопросов.
4. Запретить `--force` удалять вопросы и классификации.
5. Добавить проверки, что число вопросов и `question_topics` не уменьшается после обновления.

Без этапа A запускать новый общий пайплайн на основной базе нельзя.

### Этап B — схема и миграции

1. Перенести `questions.difficulty` и недостающие индексы в основную свежую схему.
2. Ввести версионируемые миграции вместо DDL при каждом подключении.
3. Добавить `position_in_pack`, `question_result_stats`, `pack_result_status`.
4. Явно отделить источник `gotquestions` от импортов `db.chgk`.

### Этап C — расчёт сложности

1. Вынести извлечение масок и расчёт в тестируемый модуль.
2. Добавить строгую валидацию соответствия.
3. Реализовать статусы и повторные попытки.
4. Записывать результаты атомарно и идемпотентно.

### Этап D — единый оркестратор

1. Создать `scripts/update_catalog.py`.
2. Подключить безопасный парсер содержимого.
3. Подключить очередь сложности.
4. Добавить `--dry-run`, точечный запуск и полный backfill.
5. Выдавать машинно- и человекочитаемый итоговый отчёт.

### Этап E — проверка и первый запуск

1. Все модульные тесты проходят в чистом окружении.
2. End-to-end тест работает на временной базе и сохранённых HTML-фикстурах.
3. Точечный `--dry-run` на реальных пакетах разных типов.
4. Запуск на копии текущей базы.
5. Сравнение количеств и выборочная ручная проверка 20 вопросов.
6. Только после этого — резервная копия и backfill основной базы.

## 8. Обязательные тесты

- повторный UPSERT пакета сохраняет вопросы и классификации;
- повторный запуск полностью идемпотентен;
- `--dry-run` не меняет базу;
- пакет с 0%, 50% и 100% взятий даёт ожидаемую формулу;
- неодинаковые маски не приводят к частичной записи;
- несовпадение количества вопросов не приводит к частичной записи;
- изменение результатов пересчитывает статистику по новому `source_hash`;
- новый пакет без таблицы переходит в `waiting_for_results`;
- старый пакет без результатов не запрашивается бесконечно;
- сетевой сбой получает повтор, но не портит предыдущие данные;
- импорт `db.chgk` получает `not_applicable`;
- после полного обновления число вопросов и классификаций не уменьшается.

## 9. Критерии готовности

- все текущие тесты и новые тесты проходят;
- ежедневное обновление выполняется одной командой;
- повторный запуск без изменений сообщает `0 new / 0 changed`;
- ни одно несовпадение не записывает частичную сложность;
- для каждого заполненного значения известны число команд, число взятий, метод, источник и время расчёта;
- все оставшиеся `NULL` объясняются статусами, а не являются безымянным остатком;
- физическая очистка проблемных данных не производится.

## 10. Следующие этапы после стабилизации

После безопасного обновления и сложности:

1. исправить параллельную классификацию и её воспроизводимость;
2. показывать покрытие классификации рядом с любой аналитикой;
3. построить отдельный пайплайн сущностей для фильмов и персонажей;
4. исправить поиск турниров и унифицировать тренировочный прогресс;
5. вернуться к ручному аудиту неполных и дублирующихся вопросов.

## 12. Результат производственного backfill

Полный запуск `python scripts/update_catalog.py --backfill-difficulty --retry-mismatches`
и последующий разбор исключений завершены 2026-07-16. Перед массовыми изменениями
созданы согласованные SQLite-копии, в том числе
`.backups/chgk_analysis-20260716-002045.db`,
`.backups/chgk_analysis-20260716-075734.db` и
`.backups/chgk_analysis-20260716-080248.db`.

- Первый проход сформировал 121,446 статистик вопросов. Повторная проверка 47 несовпадений масок подтвердила безопасный ID-связанный fallback: 33 пакета стали `complete`, 14 — `partial_complete`, добавлено 2,319 статистик; 35 вопросов без полных встроенных счётчиков намеренно остались без сложности.
- Для больших страниц введён адаптивный сетевой тайм-аут. Благодаря этому пакет 6676 с 649 вопросами обработан полностью: рассчитаны 648 игровых вопросов по результатам 39 команд, один вопрос №0 оставлен без сложности.
- Итоговая база содержит 124,413 статистик вопросов в 2,803 пакетах: 122,094 методом `take_rate_v1` и 2,319 методом `embedded_question_stats_v1`.
- Сложность заполнена у 124,413 из 212,779 вопросов; среднее значение `difficulty_raw` — 5.6716, диапазон — от 0 до 10.
- В полностью обработанных пакетах 944 явных разминочных/служебных вопроса намеренно оставлены без сложности; в `partial_complete` без подтверждённого значения остаются 819 вопросов.
- Итоговые статусы 4,000 разобранных пакетов: 2,632 `complete`, 171 `partial_complete`, 1 `content_mismatch`, 1,185 `no_results`, 8 `waiting_for_results`, 3 `not_applicable`. Статусов `mask_mismatch` и `retryable_error` больше нет.
- Единственное содержательное исключение — пакет 6763: в базе есть 36 вопросов, но страницы пакета и результатов на источнике недоступны, поэтому безопасно подтвердить соответствие невозможно.
- Количество пакетов, вопросов и тематических меток не уменьшилось: 6,957 / 212,779 / 52,386. `foreign_key_check` не нашёл нарушений, `quick_check` вернул `ok`.

Ранее зафиксированный список пропусков, дублей и других проблем качества исходных данных
не изменялся и остаётся отдельной задачей ручного аудита.
